# NDI Java 重构路线图

## 1. 目标与范围

NDI Java 以项目管理、排产、计收和能力指标四个业务模块为交付主线，采用 Spring Modulith 模块化单体承载首发版本。重构不以逐页复制旧 FastAPI 服务为目标，而是以稳定的业务边界、数据所有权和接口契约逐步接管业务。旧服务在过渡期用于核对既有规则与历史数据，新的业务写入只归属一个系统，避免双写产生账务、排产或指标口径分叉。

当前已完成工程骨架、Flyway 数据库演进、MySQL 本地环境、请求链路标识、统一 API 契约和基础安全拒绝策略。业务实体、状态机、计收规则和指标公式尚未提前固化，后续阶段以业务规则澄清为进入条件。

## 2. 实施原则

每个模块保有自身领域实体、数据库表和迁移脚本；跨模块仅经应用服务接口或公开领域事件协作。`projects` 持有项目主身份，排产、计收和能力指标只保存项目标识及必要业务快照。JPA 仅校验映射，表结构只通过 Flyway 版本迁移演进，不允许启动时建表或修改表。

接口层统一使用 `ApiResponse`、`PageResponse` 和 `ProblemDetail` 错误协议。领域错误码由所属模块维护，公共层不收纳项目状态、排产约束、结算规则或指标公式。单元测试覆盖领域规则，MockMvc 固化 HTTP 契约，Testcontainers MySQL 验证迁移和应用启动；高层联调用例保持少量且聚焦关键流程。

## 3. 分阶段计划

| 阶段 | 主要工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：业务梳理 | 从旧服务、前端页面和现有数据中整理术语表、角色矩阵、状态流转、字段口径与外部依赖；将结论写入 ADR 或模块设计说明。首轮事实盘点见 [P0 文档](../discovery/README.md)。 | 四个模块的边界、项目主键策略、历史数据范围及首发流程形成书面结论。 |
| P1：工程底座 | Maven、模块边界、Flyway、本地 MySQL、统一响应与错误、安全入口、审计链路、CI 验证。 | 已完成；后续仅按需求增量完善。 |
| P2：项目管理 MVP | 实现组织与身份最小模型、项目主数据、项目状态机、项目查询与命令接口、附件或关联资料入口；建立项目模块专属错误码与权限点。 | 项目可创建、查询、变更并留下审计记录；接口、迁移和权限测试通过。 |
| P3：协同能力 | 按 P2 实际需要补充审批、通知、资料和变更留痕，不预建通用流程引擎。 | 项目变更流转与资料归档满足首发场景，模块间只通过公开接口协作。 |
| P4：排产 | 在资源、工序、产能日历、约束和排产结果口径明确后，实现方案草稿、计算、发布与调整留痕；排产结果引用项目而不修改项目主数据。 | 同一输入产生可追溯结果；冲突与人工调整具备审计记录。 |
| P5：计收 | 在合同、计费对象、计收周期、确认条件、冲销和对账规则明确后，实现应收计划、实际计收、核对和期间锁定。 | 计收数据可按规则复算，与来源记录逐项核对。 |
| P6：能力指标 | 以版本化指标定义、来源映射和计算快照实现指标计算与钻取；报表模块只读交易模块公开数据。 | 任一指标均可追溯定义版本、来源数据和计算时间。 |
| P7：切换与退役 | 按模块执行历史数据演练、只读核对、增量切换和回退演练；旧服务在全部模块完成接管后退役。 | 新系统拥有唯一写入权，历史核对完成，退役范围经业务验收。 |

## 4. 数据迁移与发布策略

迁移按“抽取、映射、校验、演练、切换、回退”执行。每轮迁移保留源数据统计、主键映射、失败明细和校验结果；业务表迁移脚本与应用 Flyway 迁移分离管理。模块切换前由新系统承担只读核对，切换窗口后才开放该模块写入，任何模块均不采用长期双写。

发布以一个纵向业务切片为单位：领域规则、数据库迁移、应用服务、HTTP 接口、权限、审计和测试同时交付。排产、计收和能力指标在各自规则未成熟前只保留模块边界与接口扩展点，不建立空表、演示种子或猜测性的状态字段。

## 5. 当前优先级

下一项工作是 P0 中项目管理的规则梳理，产出项目术语、字段清单、状态流转、角色权限和旧数据映射。该产出经确认后，进入 P2 的首个纵向切片：项目列表查询与项目创建命令，并以第一份业务 Flyway 迁移、模块错误码、审计事件和 MockMvc 契约测试同步交付。

## 6. 风险控制与质量门槛

计收口径、排产约束和指标公式直接影响数据模型，未形成可验证规则前不进入建表阶段。每项业务迁移须具备幂等策略、失败报告和回退路径；每次接口变更须保持版本兼容或明确弃用窗口。合并代码前执行 `./mvnw clean verify`，通过模块架构测试、接口契约测试和 MySQL 集成测试后方可进入环境部署。

## 7. 编制依据

路线图与 [架构总览](../architecture/overview.md)、[模块化单体 ADR](../adr/0001-modular-monolith.md) 和 [公共 API 组件边界](../architecture/common-api-components.md) 保持一致。测试分层采用快速底层测试为主、少量粗粒度集成测试验证关键链路的策略。
