# ADR-0003：报表与对象存储边界

**日期：** 2026-10-15  
**状态：** 已采纳

## 背景

四个业务模块均需要汇总、趋势、区域分布和分析展示，且各模块的关注对象、指标口径和使用角色不同。旧系统仅对项目管理建立月度统计事实，排产、计收和能力指标仍停留在列表台账。旧附件直接写入应用数据目录，数据库记录相对路径；该模式使应用实例、备份与文件访问紧耦合。

## 决策

项目管理、排产、计收、能力指标分别拥有本模块的工作台或统计分析，工作台入口、指标展示、趋势、下钻和本模块读模型均归属相应业务模块。模块工作台的初始分析范围如下；具体指标定义由各模块的领域澄清材料定版。

| 模块 | 自有工作台／统计分析范围 |
| --- | --- |
| `projects` | 项目数量、阶段、进展、金额和地域等项目管理维度。 |
| `production` | 排产期间、计划状态、项目或客户和产品等排产维度。 |
| `collection` | 计收期间、业务分类、记录状态和项目关联等计收维度。 |
| `capabilities` | 指标分类、组织范围、期间和状态等能力指标维度。 |

`reporting` 保留为跨模块只读分析边界，不新增统一工作台或统一大屏入口。它承载跨模块专题报表、跨模块汇总读模型和经定版后复用的分析能力；它不接管任一业务模块的日常工作台。业务模块对外发布稳定的公开事件或查询投影，跨模块分析只基于这些公开契约构建。所有统计查询均按当前用户的数据范围执行，分析模块不直接修改业务数据。

保留 `documents` 模块并将其定义为附件与文档能力。MinIO 是 S3 兼容对象存储，不承担关系型数据职责：对象内容存入 MinIO，MySQL 保存文档标识、对象键、原文件名、媒体类型、字节数、哈希、版本、上传人、存储状态和删除审计。业务模块通过文档标识关联项目、进展、审批、排产、计收或能力指标记录，不保存本地绝对路径或对象键作为业务字段。

上传采用“申请上传—对象写入—完成校验”流程。`documents` 生成不可猜测的对象键和限时上传凭证；完成后核对对象存在性、大小、媒体类型和哈希，再将文档置为可用。下载由业务模块先完成数据范围与业务权限判断，再由 `documents` 签发限时读取凭证。物理删除延后执行，已被审计或审批引用的文档保留逻辑删除记录。

## 后果

每个业务模块在自身包边界内维护工作台所需的查询服务和读模型；`reporting` 仅维护 `cross` 范围的跨模块读模型与专题查询，不按四个业务模块复制子包。模块工作台不得直接读取其他模块的实体或仓储；需要跨模块数据时，通过公开事件、查询投影或 `reporting` 的专题查询取得。首发不引入数据仓库、消息队列或单独部署单元。数据量、刷新时效或跨系统分发达到明确需求后，再以 ADR 评估增量同步、Outbox 或分析存储。

`documents` 在项目管理首个纵向切片中只建立文档元数据、项目附件关联和 MinIO 上传下载闭环；审批截图等其他文件在对应模块接入。数据库备份与对象存储备份通过同一备份清单关联，恢复演练同时校验记录数、对象键和哈希。开发环境沿用现有 Compose 中的 MinIO 服务，生产环境凭据仅由环境变量或密钥管理系统提供。
