# P0：项目管理规则澄清

**状态：** P0 项目管理基线，具备进入 P2 详细设计条件

**范围：** `projects` 模块的项目主身份、项目生命周期、过程记录、权限、导入和模块内统计分析

**不在范围内：** 排产、计收、能力指标的领域规则；对象存储实现；通用流程引擎；业务 Flyway 迁移

## 1. 结论与使用边界

`projects` 持有项目主身份和项目生命周期，其他业务模块只保存项目标识及必要业务快照。项目工作台／统计分析属于 `projects`，其查询模型只读取本模块公开数据；`reporting` 只处理跨模块专题分析，不承接项目工作台。

本文件将旧系统中的已验证事实、当前实现行为和新系统规则分开描述。P2 以本文件、[参考数据字典](p0-project-reference-data.md)和[定版决策清单](p0-project-management-open-decisions.md)为设计输入；首个纵向切片不包含项目合并、历史审批迁移、历史附件迁移和历史月末快照读模型。

## 2. 领域术语

| 术语 | 定义 | 边界与约束 |
| --- | --- | --- |
| 项目 | 以稳定项目标识管理的一项工业三化业务机会或已签约事项。 | 项目名称是展示和查重依据，不是跨模块关联键。 |
| 项目编号 | 项目生效后生成的业务可读编号。 | 草稿不占用编号；编号生成规则须可审计。 |
| 项目主身份 | 用于跨模块引用的不可复用项目标识。 | 项目更名、属地调整或历史迁移不得改变该标识。 |
| 项目生命周期阶段 | 项目在项目管理范围内的当前业务位置。 | 当前阶段由已生效里程碑推导并冗余保存；不得以直接覆盖方式改写历史。 |
| 阶段里程碑 | 项目进入某个阶段的一次事实记录。 | 包含阶段、生效日期、来源、操作人和说明；同一阶段再次进入时新增记录。 |
| 项目进展 | 对项目当前进展、下一步动作、责任和支撑诉求的追加式记录。 | 已保存记录不物理删除；纠错通过新增更正记录关联原记录。 |
| 重大变更 | 由属地填报职责或省级统筹职责通过指定入口主动发起的受控修改。 | 系统不按金额阈值自动识别；申请保存版本、前后值和变更原因，审批前不覆盖生效值。 |
| 项目属地 | 项目归属的省分和地市。 | 地市必须隶属所选省分；数据范围基于授权组织树计算。 |
| 项目责任 | 对项目承担省分统筹、地市客户、产品支撑等职责的人员关系。 | 人员目录与登录账号分离，关系中保留人员名称快照。 |
| 历史导入 | 将旧系统或 Excel 中的项目记录纳入新系统的受控过程。 | 保留源系统、批次、工作表、行号、原始值、转换结果和处置结果。 |

## 3. 模块职责与聚合边界

项目主身份、项目基础资料、阶段里程碑、进展、责任关系、名称别名、变更申请和项目专属导入属于 `projects`。附件内容与对象元数据属于 `documents`，项目只保存文档关联；身份、组织和数据范围权威来源属于 `identity` 与 `organization`；审批任务的通用执行能力属于 `workflow`，项目模块只定义何种项目变更需要审批以及审批通过后的业务生效动作。

项目金额在项目管理中仅表达商机或项目预期金额及其确认状态，不承担合同、应收、实收、冲销和对账职责。项目生命周期固定包含“计收”阶段，它表达项目已进入计收管理的业务位置；`collection` 持有计收计划、实际计收、冲销和对账等明细。单笔计收记录不得直接改写项目阶段，项目进入计收阶段须由 `projects` 的审批生效动作完成。

## 4. 候选字段清单

字段按业务含义分组，而非照搬旧库表。字段代码在定版后再确定；本节用于确认首发数据最小集、字段归属和导入要求。

| 字段组 | 候选字段 | 规则与来源 | 首发口径 |
| --- | --- | --- | --- |
| 主身份 | 内部项目标识、项目编号、记录状态、版本号 | 旧系统以 UUID 和 `Project_ID` 区分内部关联与业务展示。 | 生效项目必须具有内部标识、编号和乐观锁版本；草稿独立保存。 |
| 组织属地 | 省分、地市、组织名称快照 | 旧系统以省市字典校验归属和查询范围。 | 省市关联由 `organization` 校验；项目保存引用及名称快照策略由迁移方案定版。 |
| 名称与客户 | 项目名称、名称标准值、名称核心值、历史别名、客户名称、客户行业 | 旧系统按同地市名称查重，名称变更保留别名。 | 项目名称为必填；客户名称的在线新建与历史导入规则分开处理。 |
| 建设内容 | 原始建设内容、客户需求、产品推进内容、应用场景、备注 | 旧台账中的建设内容存在半结构化标签文本。 | 原始值保留，结构化字段仅在有明确来源或人工录入时写入。 |
| 项目分类 | 三化类别、重要度、签约主体 | V1.2 增加签约主体，废弃三化标杆和总投总签标签。 | 类别采用稳定代码和分类金额的多值关系；废弃字段不进入新业务接口。 |
| 生命周期 | 当前阶段、阶段日期、最近活动时间、统计归属月份 | 阶段固定为方案交流、招投标、签约、计收和已终止；阶段变化产生里程碑。 | 两类时间的更新条件须以定版状态机为准。 |
| 预期金额 | 项目总金额、分类预计金额、拟招标日期及精度 | 金额单位为万元；项目总金额为首发必填。 | 金额使用定点小数；项目总金额与已选类别金额均为非空、非负数值；分类金额合计不得超过项目总金额。 |
| 项目责任 | 省分负责人、地市客户经理、产品单位支撑专家及其他协作职责 | V1.2 用组织与责任信息组替代旧“项目负责人”单字段。 | 省分负责人关联本省已启用的省分三化、数字化或智能化负责人账号；地市客户经理以必填自由文本保存；人员名称快照保留于关系记录。 |
| 过程记录 | 进展日期、进展内容、下一步动作、下一步责任、到期日、支撑诉求、更正关联 | 旧系统采用追加式进展和更正说明。 | 进展正文与下一步动作不得为空；重点项目到期日规则需定版。 |
| 治理与来源 | 建立来源、导入批次、来源行号、创建人与时间、更新人与时间、规则版本 | 旧系统留存在线／导入来源、批次和行号。 | 迁移、审批和规则调整均须保留来源与版本证据。 |

下列字段不纳入 `projects` 的首发业务模型：附件对象键、附件本地路径和文件哈希属于 `documents`；应收、实收、冲销和对账属于 `collection`；排产结果属于 `production`；能力计算结果属于 `capabilities`。合同编号和签约金额属于项目进入计收阶段的单合同凭据，作为 `projects` 的阶段审批字段保存；它们不构成计收模块的合同、应收或实收模型。旧系统本地附件路径只作为历史源字段参与迁移评估。

## 5. 状态与变更规则

项目管理至少存在三个彼此独立的状态轴。将草稿、项目是否有效、项目阶段和审批进度混在单一状态字段中，会造成列表、权限和统计口径相互污染。

| 状态轴 | 候选状态 | 约束 |
| --- | --- | --- |
| 草稿 | 编辑中、已提交、已放弃 | 草稿不是生效项目，不参与项目编号、查重结果和工作台统计。 |
| 项目记录 | 生效 | 已终止属于生命周期阶段而非记录删除；项目合并不在 P2 范围，不设置合并状态或合并接口。 |
| 项目生命周期 | `SOLUTION_EXCHANGE` 方案交流、`BIDDING` 招投标、`SIGNED` 签约、`COLLECTION` 计收、`TERMINATED` 已终止 | 当前阶段来自最新生效里程碑；阶段代码固定，已中标不再作为有效阶段；`TERMINATED` 是首发终态，不允许恢复。 |
| 变更申请 | 待审批、已通过、已驳回、已撤回、冲突 | 一条申请在发起时冻结唯一审批人；待审批申请不覆盖项目生效值，审批时校验申请基础版本。 |

项目生效的创建动作应在同一事务内完成项目主身份、首条里程碑、首条进展、责任关系和审计记录。正向路径固定为“方案交流 → 招投标 → 签约 → 计收”，每次正向阶段推进均提交审批；审批通过后才写入新里程碑并更新当前阶段。阶段变化不得覆盖既有记录；`TERMINATED` 是不可恢复的终态。名称、金额、阶段回退和终止均通过重大变更入口由用户主动发起，项目合并不在 P2 范围。

重大变更审批通过后，项目回退至低于 `SIGNED` 的阶段时，当前项目的合同编号和签约金额必须清空；被清空值留存在变更申请、变更明细和审计记录中。终止项目不清空任何已生效字段，合同编号和签约金额等既有字段继续作为历史事实保留。项目进入或停留在 `SIGNED`、`COLLECTION`、`TERMINATED` 时，合同编号和签约金额均允许保留。

审批申请提交时记录 `submitted_at` 和唯一审批人，截止时间固定为 `submitted_at + 48` 小时，不因周末或法定节假日顺延。逾期扫描每 24 小时执行一次，仅向该审批人发送提醒；提醒不自动通过、驳回或升级申请。驳回必须填写意见，发起人撤销后保留审计；驳回后的修改以新申请处理。方案交流推进招投标须提交客户侧交流方案，招投标推进签约须提交中标通知书，签约推进计收须填写全局唯一合同编号和签约金额。终止、回退以及名称、金额等重大变更只要求变更原因，不要求上传材料。管理员不拥有业务审批权限。

## 6. 权限矩阵

新系统不将旧系统角色代码直接固化到 `projects`。`identity` 与 `organization` 提供用户、角色、组织范围和授权关系；项目模块仅校验权限点、项目状态和数据范围。下表以旧系统已验证职责为基础，表示首发所需的能力集合，不表示最终角色命名。

| 权限点 | 属地填报职责 | 省级统筹职责 | 审核职责 | 平台管理职责 | 关键约束 |
| --- | --- | --- | --- | --- | --- |
| `project:read` | 查看授权属地项目 | 查看授权省级范围项目 | 查看获授权审核范围项目 | 仅为配置、导入诊断取得最小定位信息 | 服务端按组织范围过滤，前端隐藏不构成授权。 |
| `project:create` | 在授权属地创建项目和草稿 | 在授权省级范围创建项目和草稿 | 无 | 无 | 省市由当前授权范围校验，不采信客户端传值。 |
| `project:update_normal` | 维护授权属地项目 | 维护授权省级范围项目 | 无 | 无 | 常规字段维护不含阶段、名称、金额、合同编号和签约金额；进展保持追加式。 |
| `project:append_progress` | 在授权属地追加进展 | 在授权省级范围追加进展 | 在获授权审核范围追加进展 | 无 | 仅新增进展，不修改既有进展或项目主字段。 |
| `project:upload_document` | 向授权项目或审批申请上传资料 | 向授权项目或审批申请上传资料 | 向获授权审核范围的项目或审批申请上传资料 | 无 | 文件内容由 `documents` 写入 MinIO，项目只保存文档关联。 |
| `project:advance_stage` | 对授权项目发起正向阶段审批 | 对授权项目发起正向阶段审批 | 处理发起时指定给本人的审批节点 | 无 | 审批通过后才写入里程碑和当前阶段。 |
| `project:request_change` | 对授权项目发起受控变更 | 对授权项目发起受控变更 | 无 | 无 | 申请冻结项目版本、规则版本和前后值。 |
| `project:review_change` | 无 | 无 | 仅处理分配给本人的审批节点 | 无 | 申请人与处理人职责分离，审批范围由任务快照约束。 |
| `project:import` | 仅导入授权属地的历史或新增项目 | 仅导入授权范围项目 | 仅导入获授权审核范围的项目 | 全国历史迁移按独立授权执行 | 每行均执行省市、字段和金额校验；名称查重策略不在首个纵向切片范围。 |
| `project:export` | 导出授权范围结果 | 导出授权范围结果 | 导出获授权审核范围结果 | 无 | 导出继承读取范围，排除附件内容和运行敏感信息。 |

项目责任信息不构成逐项目授权。首发权限按角色与省市数据范围计算：被填写为省分负责人、地市客户经理或产品单位支撑专家的人员，不因该信息自动取得读取、编辑或审批权限。接口人无项目创建、普通字段编辑和责任信息修改权限；其可执行追加进展、上传资料、授权范围内的 Excel 项目导入及分配给本人的审批。首发不建立项目协作授权；管理员不参与业务审批。

## 7. 历史数据映射策略

历史迁移不采用旧库结构的逐表复制。每批迁移执行“抽取、标准化、预校验、人工处置、确认写入、核对与回退”闭环，迁移过程保留源记录而非覆盖源数据。项目主身份映射表、导入行结果、错误与预警代码、原始行内容和转换后字段均属于迁移审计证据。

| 旧来源 | 新项目管理归属 | 映射规则 | 处置要求 |
| --- | --- | --- | --- |
| 旧 `project` 主档 | 项目主身份与基础资料 | 旧项目 ID 仅作为源标识；新项目标识与业务编号按新规则生成。 | 保存源系统、源主键、导入批次和映射结果。 |
| 旧 `project_finance` | 预期金额与拟招标时间 | 金额按万元、定点两位小数导入；空值与零值保持语义差异。 | 分类金额超总额、负数或非法数值阻断该行。 |
| 旧 `project_category` | 项目分类关系 | 按定版分类字典映射稳定代码。 | 无法识别的类别进入处置清单，不以自由文本代替代码。 |
| 旧 `project_member` 与负责人文本 | 项目责任关系及原始责任文本 | 优先映射 V1.2 的省分负责人、地市客户经理和产品支撑专家；无法可靠拆分时保留原文。 | 缺失必填责任字段的历史项目进入质量清单，不阻断历史只读核对。 |
| 旧 `stage_milestone` 与当前阶段 | 生命周期阶段及里程碑 | 已中标统一映射为招投标；计收保留为有效项目阶段；缺失里程碑补录规则由迁移方案明确。 | 系统迁移生成的记录必须标识迁移来源，不伪造人工操作人。 |
| 旧 `project_progress` | 追加式进展记录 | 保留进展日期、内容、下一步、责任、到期日和来源顺序。 | 无法解析的日期或空内容分别进入失败或质量处置清单。 |
| 旧 `change_request`、`approval_task`、`audit_log` | 不纳入首轮迁移 | 旧审批和审计不在新系统继续流转。 | 保留旧系统只读核对范围。 |
| 旧 `project_attachment` 本地文件 | 不纳入首轮迁移 | 新增文件由 `documents` 和 MinIO 承载。 | 保留旧系统只读核对范围，不迁移本地绝对路径或文件内容。 |
| Excel 样例与导入批次 | 受控导入批次 | 按工作表、表头、行号和人工映射进行标准化。 | 强重复、候选重复、失败和质量预警分别记录，禁止静默修正。 |

首轮迁移纳入所有记录状态为有效的项目，包括当前阶段为已终止的项目；同时迁移项目主档、历史进展、阶段里程碑、责任信息和导入来源。审批、审批审计与附件不迁移。导入项目必须具备客户名称、客户所属行业、省分负责人、地市客户经理、阶段、三化类别和项目总金额等核心字段；缺失核心字段的来源行应在预检中修正后再写入。迁移验收至少核对项目数、稳定映射数、失败数、预警数、阶段分布、金额汇总和抽样项目的时间线完整性。新旧系统切换前，新系统先承担只读核对；开放写入后不得长期双写。

## 8. 项目工作台与统计分析

`projects` 工作台面向本模块的待办、风险和项目经营视图，按当前用户的数据范围执行。首发不建设历史月末快照读模型，也不维护会回写旧月份的唯一归属月事实表。默认经营指标和阶段分布均排除已终止项目；如有分析需要，可通过显式筛选将其纳入。项目总金额不得为空。未来月末快照从项目的不可变里程碑和版本化变更记录生成，以回答某一月份月末的项目存量与金额状态。

统计读模型只能从 `projects` 的生效项目、里程碑、进展和经定版的项目金额快照构建。项目工作台不读取排产、计收或能力指标的私有表；需要呈现跨模块经营关系时，由 `reporting` 建立专题分析并使用各模块公开契约。
