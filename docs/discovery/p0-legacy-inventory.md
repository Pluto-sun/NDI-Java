# P0：旧系统事实盘点与新系统映射

## 1. 盘点范围与结论

本轮盘点覆盖旧项目的需求说明、字段字典、V1.2 设计、FastAPI 模型与路由、React 菜单及运营台账模板。旧系统已形成较完整的项目主档、进展、变更审批、导入、项目月度事实和项目工作台能力；排产、计收、能力指标则共用 `operations_record` JSON 台账。新系统不迁移该通用表结构，而将其作为历史数据和字段梳理来源，分别落入 `production`、`collection`、`capabilities` 模块。

## 2. 旧系统已验证的业务事实

| 范围 | 已存在事实 | 新系统归属 |
| --- | --- | --- |
| 项目主档 | 唯一项目编号、省市、客户、名称、建设内容、类别、金额、阶段、责任人、版本号与审计。 | `projects` |
| 项目过程 | 阶段里程碑和进展均为追加式记录；重大变更含申请快照、审批任务和审计。 | `projects`、`workflow` |
| 项目统计 | `project_monthly_fact` 为项目管理提供月度数量、金额、阶段和区域趋势。 | `reporting` 读取 `projects` 公开数据 |
| 排产 | 月度排产计划含省市、项目或客户文本、产品收入和项目状态。 | `production` |
| 计收 | 网络化、数字化、智能化三类台账具有不同字段和锁定规则。 | `collection` |
| 能力指标 | 智能化部署、上线、开发中，以及数字化部署、自动运维、手工填报等台账。 | `capabilities` |
| 附件 | 项目附件和上线审批截图写入服务目录，数据库保存相对路径、名称和哈希。 | `documents` + MinIO |

旧系统工作台只统计项目月度事实；排产、计收和能力指标页面以各自台账列表呈现，驾驶舱页面仍处于占位状态。运营台账大量记录仅保存项目名称、客户名称和省市文本，缺少稳定项目关联，因此历史迁移必须保留原始文本、生成匹配结果和人工处置记录，不能按名称直接写入项目外键。

## 3. 新旧边界映射

新系统以 `projects` 持有项目身份和项目生命周期。`production`、`collection`、`capabilities` 各自持有领域数据、期间、状态和规则，只引用项目标识及在写入时固化的名称、客户、省市等业务快照。`reporting` 建立只读指标和趋势模型，不回写交易模块。`documents` 管理附件元数据、对象版本和存储状态，业务模块仅保存文件关联。

旧系统的 `operations_record` 不作为新系统实体原型。其 JSON 字段适合快速承接变化频繁的 Excel 模板，却无法表达排产计划、计收确认和能力指标的独立约束、关联与统计口径。新模块建模前将以现有模板、导入记录和业务访谈形成字段字典，再决定关系表、快照和导入映射。

## 4. P0 需形成定版结论的事项

项目阶段在旧需求、V1.2 设计和前端行为中存在“已中标”与“计收”阶段取舍差异，项目生命周期、阶段推进是否审批、阶段日期口径须统一为一份规则。排产、计收、能力指标须分别明确业务主键、期间定义、可修改范围、审批条件、作废或冲销规则、与项目的关联强度及历史模板保留范围。

跨模块统计还须形成指标字典：指标名称、统计主体、时间口径、维度、权限范围、来源模块和重算规则。附件须确定允许的文件类型、单文件上限、保留期限、删除语义和上传后的病毒扫描要求。身份与组织须明确账号来源、组织层级、角色与数据范围的权威来源。

## 5. P0 下一步产出与完成标准

项目管理优先形成术语表、字段字典、状态机、角色权限矩阵、首发用例清单和旧数据映射表。排产、计收、能力指标各形成一份同结构的领域澄清清单。每项结论需给出业务负责人、样例数据、验收场景和影响模块；出现规则分歧时通过 ADR 或模块设计说明记录取舍。上述材料完成后，项目管理进入第一份业务 Flyway 迁移与首个纵向接口实现。
