# P3：项目普通信息维护切片实施记录

## 范围与业务边界

项目管理已有创建、详情、进展和审批接口，尚缺 P0 权限矩阵规定的普通字段维护。本切片补充项目主档的客户名称、客户所属行业、客户需求、省分负责人和地市客户经理维护。项目名称、总金额、分类金额、阶段、合同编号及签约金额均不进入该命令；其中名称、总金额和阶段继续按既有重大变更或阶段推进审批生效。未建立新业务表，数据库结构保持在现有 Flyway 版本。

地市填报职责仅维护本地市项目，省分三化、数字化、智能化负责人维护本省项目；接口人和管理员不具有普通信息修改权限。省分负责人仍须是本省已启用且具有对应省级负责人角色的账号，行业代码须存在且已启用。已终止项目拒绝普通信息修改，详情和历史记录不受影响。

## 写入机制与接口

`PUT /api/v1/projects/{projectId}/profile` 使用完整替换请求，包含 `expectedVersion` 和上述五项普通字段。正文去除首尾空格，字段非空且遵守库表长度限制；行业代码统一为大写。固定字段集合避免将空缺字段误作清除，也避免通过普通入口绕过审批字段。成功响应为更新后的项目详情，版本冲突返回 `409`，字段或引用不合法返回 `400`，越权返回 `403`，终止后写入返回 `409`。

服务端先锁定项目并校验角色、属地、终止状态和客户端版本，再校验行业与负责人。内容实际变化时，事务内更新主档版本、修改人和修改时间，并写入带变更前后字段值的 `PROJECT_PROFILE_UPDATED` 事件。相同内容的重复请求不增加版本、不生成空审计事件。普通信息变更允许发生在待审批期间；审批处理仍按原有基础版本校验，旧申请在版本变化后进入冲突状态，避免覆盖已生效的新资料。

## 验证与后续边界

MySQL 集成测试覆盖字段清洗与保留受控字段、变更前后审计值、重复请求不增版本、旧审批申请冲突、接口人及管理员禁写、跨地市拒绝、过期版本、无效行业与负责人、已终止项目只读和 HTTP 必填校验。执行 `./mvnw clean verify` 同时检查既有审批、MinIO、架构边界和数据库迁移。

本次不扩展应用场景、产品单位支撑专家等尚未落入主档的可选字段，也不改变历史导入或月末快照。采用完整替换意味着客户端应先读取详情及版本，再提交全部五项普通字段；若另有客户端需要单字段补丁，应在字段缺省与显式清空语义定版后增加独立契约。管理员的数据修复能力应走独立、可审计的运维流程，不借用业务维护接口。
